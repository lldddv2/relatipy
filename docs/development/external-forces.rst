External forces and potentials
==============================

This page fixes the contract of the external-force layer: a perturbed Kerr
geodesic integrated beside, not inside, the homogeneous Kerr path. Existing
Kerr modules, integrators and the ``_core`` and ``_mcmc_core`` extensions are
not modified; the new layer only calls them. The user-facing description is
:doc:`/user-guide/forces`.

Equation of motion
------------------

In Boyer--Lindquist coordinates ``(t, r, theta, phi)``, signature
``(-,+,+,+)`` and geometric units with the black-hole mass set to one, the
perturbed geodesic is

.. math::

   \frac{du^\mu}{d\tau} + \Gamma^\mu{}_{\alpha\beta} u^\alpha u^\beta = f^\mu,
   \qquad f^\mu = \left(g^{\mu\nu} + u^\mu u^\nu\right) F_\nu .

The homogeneous term is the corrected Levi--Civita connection of the Kerr
metric, evaluated by the kernel used by every homogeneous production path:
``rp_kerr_geodesic_physic_evaluate_generated_rhs``
(``native/src/geodesic/physic/kerr_rhs_generated.c``), the kernel behind
``rp_kerr_null_geodesic_rhs``, generated by ``relatipy._codegen``. The generic
contraction ``rp_kerr_geodesic_physic_evaluate_corrected_rhs`` is kept as its
test reference. Consequently:

- with an inactive force (a NULL force or a NULL callback) trajectories and
  observables are bitwise those of ``_core`` and ``_mcmc_core``;
- a zero active force (a thin disk of zero mass, ``Potential("0")``)
  adds a zero four-acceleration to the same right-hand side, so ``dop853``
  and ``dp45`` results are also bitwise those of the homogeneous paths.
  Forced ``radau`` orbits use a finite-difference Jacobian instead of the
  analytic one, so they agree only to the integration tolerance.

The projector keeps ``u_mu f^mu = 0``, so ``g_(mu nu) u^mu u^nu = -1`` is
preserved. The covector ``F_nu`` is built from a Newtonian acceleration
``a`` evaluated in the black-hole Cartesian frame

.. math::

   x = \sqrt{r^2 + a_*^2}\,\sin\theta\cos\phi,\quad
   y = \sqrt{r^2 + a_*^2}\,\sin\theta\sin\phi,\quad
   z = r\cos\theta ,

as ``F_t = 0`` and ``F_i = a . dx/dx^i`` for ``i = r, theta, phi``, where
``a_*`` is the spin length. For a potential, ``a = -grad Phi`` and
``F_nu = -partial_nu Phi``. At ``M = 0`` these coordinates are flat oblate
spheroidal coordinates, so the coupling reduces exactly to Newtonian motion.

For a static potential that is axisymmetric about the spin axis,
``E' = -u_t exp(Phi)`` and ``L' = u_phi exp(Phi)`` are exact invariants of
this equation; tests use them to validate the projection. Carter's constant
is not conserved, so the forced layer always rejects ``projection_radau``,
whatever the force (``rp_kerr_forced_check_method``). Radau uses the analytic
Kerr Jacobian only for an inactive force and finite differences otherwise.

Native callback
---------------

Every force, built in or compiled at run time, is one native function::

    typedef int (*rp_external_acceleration_fn)(
        const double position[3],  /* black-hole Cartesian frame */
        const double velocity[3],  /* dx/dt in the same frame */
        const void *model,         /* read-only model data */
        double acceleration[3]     /* Newtonian acceleration */
    );

It returns zero on success. A nonzero value is reported as
``RP_FORCE_STATUS_CALLBACK_FAILURE`` by the direct evaluators, as an RHS
failure by the integrators (``Solution.status == -1``) and as an integration
failure by the observable evaluators
(:class:`~relatipy.geodesic.IntegrationError`, ``-inf`` in the likelihood).
Callbacks generated at run time return one when an acceleration component is
not finite; the tabulated thin disk fails at the centre ``r = 0`` and for a
NULL model.

Model data are immutable during an integration, own no global state and are
safe to share between threads. Units are geometric with the black-hole mass
set to one: lengths in ``G M / c^2``, times in ``G M / c^3``. Two layouts are
used:

- parameter-only models (every run-time force) read
  ``const double *model``, ``model[i]`` being the ``i``-th declared parameter;
- the tabulated thin disk reads an ``rp_axisymmetric_model``: a borrowed table, the
  mass, the length scale and a rotation built from the symmetry axis.

No Python callback runs inside an integrator.

Layout
------

- ``native/src/force/``: callback types, the frame map and projection
  (``external.c``), the forced right-hand sides in proper and coordinate time
  (``kerr_forced.c``), the forced trajectory solve (``solution/solve.c``) and
  the forced observable model (``kerr_mcmc.c``), parallel to ``geodesic/``.
- ``native/src/force/generated/``: C generated by ``tools/codegen/generate.py``
  from the specifications in ``tools/codegen/specs/`` (``projection``,
  ``ring_field``); each file names its specification and the command that
  regenerates it. Do not edit them by hand. The ``kerr_rhs`` specification
  writes the Kerr kernel beside the Kerr physics, in
  ``native/src/geodesic/physic/kerr_rhs_generated.{c,h}``.
- ``native/src/force/models/``: the built-in ``thin_disk`` on the generic
  ``axisymmetric_table``, with its ``elliptic`` and ``quadrature`` helpers.
- ``native/tests/force/``: C tests, with analytic test-only models in
  ``force_test_models.h``; build commands are in ``native/README.md``.
- ``bindings/cython/_force_core.pyx``: the private ``relatipy._force_core``
  extension (see :doc:`/development/architecture`).
- ``relatipy._codegen``: symbolic optimizer that turns SymPy expressions,
  matrices and tensors into optimized C99, and builds the source of a
  callback from a potential or a force (``build_force_source``). SymPy is an
  optional dependency (``relatipy[symbolic]``) imported only when needed.
- ``relatipy._jit``: compiles generated C with ``$CC`` (or ``cc``) and
  ``-std=c11 -O3 -fPIC -shared`` into a shared library cached in
  ``$RELATIPY_CACHE_DIR`` or ``~/.cache/relatipy/jit``, keyed by a hash of the
  source, compiler identity, flags, RelatiPy version and platform, and
  returns the callback address. Libraries are written atomically, so
  concurrent processes never load a partial file. It builds ``.so`` files and
  so supports POSIX systems only.
- ``relatipy.forces``: public force values (``Force``, ``Potential``,
  ``ThinDisk``) and the private bound-force handle.
- ``relatipy.metrics.PerturbedKerr``: Kerr plus one force, with the orbit API
  of :class:`~relatipy.metrics.Kerr`; its orbits are a private ``Orbit``
  subclass (``relatipy.geodesic._forced_orbit``) that integrates through
  ``_force_core``.
- ``relatipy.observables``: ``PerturbedKerrMcmcModel`` and
  ``PerturbedKerrMcmcMultiModel``, parallel to the homogeneous models.

Python binding of a force
-------------------------

A force is an immutable value with named parameters. Binding it to a
black-hole mass gives a private handle with three things: the callback
address, the model-data address and references that keep the callback's
library or table alive. Parameters are converted to geometric units by their
dimensions (a quantity of length dimension ``L``, time ``T`` and mass ``M``
is divided by ``r_g**L t_g**T M**M``) and written into the model data in
place, so an MCMC sampler updates the mass, a disk mass or a normal between
proposals without rebuilding a table or recompiling. Directions are given in
the black-hole frame for ``PerturbedKerr`` and in observer axes
``(Dec, RA, away)`` for the MCMC models, mapped through the proposal's spin
frame. Handles are never pickled with their addresses: forces pickle by
their C source (run-time forces) or constructor arguments (built-ins), and
native resources are recreated on first use in each process.

String definitions of run-time forces are parsed with
``sympy.parse_expr``, which uses ``eval``; restricted names and syntax
are checked first, but strings must still come from trusted input.

Built-in model
--------------

The library ships one built-in model, the fiducial thin disk below. Other
mass models are written as a :class:`~relatipy.forces.Potential` or
:class:`~relatipy.forces.Force`; the strict ``E'`` and ``L'`` tests use a
Plummer sphere compiled that way, whose acceleration is the exact gradient of
its potential.

Thin disk
   The razor-thin power-law disk of Piran et al. (2026),
   ``Sigma(R) proportional to R^alpha`` with ``alpha = -1`` between ``R_in``
   and ``R_out``, each ring softened with ``H = eps R'`` (``eps = 0.01``). Its
   acceleration is a sum of ring fields with complete elliptic integrals,
   tabulated once for unit mass and ``R_out = 1`` as the smooth combinations
   ``A = -r^3 a_d / d``, ``C = -r^3 a_z / z`` and ``P = -r Phi`` and
   interpolated with tensor-product C2 cubic splines stored as bicubic
   Hermite data, with a self-similar inner continuation and an exact
   multipole far field. A table depends only on ``alpha``, ``R_in / R_out``
   and ``eps`` (about 1 s and 11 MB to build); the disk mass, ``R_out`` (any
   length) and the disk normal are model parameters. The potential and the
   acceleration are separate interpolants that agree to about ``5e-7``
   (median) and ``9e-6`` (worst) inside the softened plane, which bounds how
   well ``E'`` and ``L'`` computed from the tabulated potential are conserved.

The Python layer caches built tables per shape in each process (a few
shapes), and every placed model keeps its table referenced.
